画像アップロードフロー

R2 規約

項目内容
キー形式{listId}/{uuid}-{sanitized-filename}
ファイル名は /[^a-zA-Z0-9._-]/g → "_" でサニタイズ
KEY_PATTERN/^[a-f0-9-]{36}\/[a-f0-9-]{36}-[\w.-]+$/i（GET 時に検証）
最大サイズ5 MB (5 * 1024 * 1024)
許可 MIMEimage/*（.startsWith("image/") チェック）
DB 保存 URL/api/images/{key}（R2 直 URL は非公開）
キャッシュCache-Control: public, max-age=31536000
ソフトデリート時R2 オブジェクトは削除しない（deletedAt を DB に記録するだけ）
ルーム削除時の R2 カスケード処理

DELETE /api/lists/:id は次の順序で処理する:

  1. DB から items を全件取得（ソフトデリート済みも含む）
  2. 各アイテムの imageUrl から /api/images/ プレフィックスを取り除いてキーを取得し、BUCKET.delete(key) を呼ぶ
  3. DB トランザクション内で items → lists の順に物理削除
R2 削除はトランザクション外で行うため、R2 削除成功後に DB 削除が失敗した場合、孤立したレコードが残る可能性がある。現状はシンプルさを優先してこの順序を採用。
// src/server/routes/lists.ts (DELETE /:id の実装要旨)
for (const item of itemsToDelete) {
  if (item.imageUrl) {
    const key = item.imageUrl.replace("/api/images/", "");
    await c.env.BUCKET.delete(key);
  }
}
await db.transaction(async (tx) => {
  await tx.delete(items).where(eq(items.listId, id));
  await tx.delete(lists).where(eq(lists.id, id));
});

バリデーション規約

すべてのリクエスト検証に @hono/zod-validator の zValidator を使用。zod スキーマはルートファイルにインライン定義（共有スキーマファイルなし）。

zValidator ターゲット使用エンドポイント
"json"POST /api/lists, PATCH /api/lists/:id, PATCH …/items/:itemId
"form"POST …/items（multipart/form-data + File）

エラー応答規約

すべてのエラーレスポンスは { error: "メッセージ文字列" } 形式の JSON。

ステータス用途例
400MIME/サイズ違反、復元対象が未削除など{ error: "File too large (max 5MB)" }
404指定 ID のリスト/アイテムが不在{ error: "List not found" }
500未捕捉例外（app.onError でキャッチ）{ error: "Internal Server Error" }

意図的に存在しないもの

設計上の意図的な省略

  • 認証ミドルウェアなし — ルーム UUID が共有鍵として機能。URL を知っている人がアクセス・編集できる設計。
  • CSRF/Origin チェックなし — Astro と Hono が同一オリジンで動作するため不要と判断。
  • CORS 設定なし — 同一オリジン前提。
  • 共有 zod スキーマファイルなし — フロント・バック間の型共有は src/lib/api.ts の型定義のみ。zod はルート内インライン。
  • AppType は現在未利用 — src/server/index.ts が Hono RPC 対応の AppType をエクスポートしているが、クライアントからは使っていない（将来の RPC 移行への準備）。
