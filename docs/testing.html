ルートテストのモックパターン

vi.hoisted でチェーン可能な mockDb を作り、vi.mock でモジュールを差し替える。テストは route.request() で HTTP 直叩き。

モックパターン全体像 (src/server/routes/lists.test.ts より) 
// 1. vi.hoisted で mockDb を作成（vi.mock 巻き上げより先に実行される）
const { mockDb } = vi.hoisted(() => {
  const mockDb = {
    select:  vi.fn().mockReturnThis(),
    from:    vi.fn().mockReturnThis(),
    where:   vi.fn().mockReturnThis(),
    orderBy: vi.fn().mockReturnThis(),
    limit:   vi.fn().mockReturnThis(),
    get:     vi.fn().mockResolvedValue(null),
    insert:  vi.fn().mockReturnThis(),
    values:  vi.fn().mockResolvedValue(undefined),
    update:  vi.fn().mockReturnThis(),
    set:     vi.fn().mockReturnThis(),
    delete:  vi.fn().mockReturnThis(),
    transaction: vi.fn(),
  };
  return { mockDb };
});

// 2. createDb をモックに差し替え
vi.mock("../db", () => ({
  createDb: vi.fn(() => mockDb),
}));

// 3. テスト本体
beforeEach(() => { vi.clearAllMocks(); });

test("GET /api/lists returns 200", async () => {
  mockDb.from.mockReturnValueOnce({
    orderBy: vi.fn().mockResolvedValue([{ id: "1", name: "test" }]),
  });

  const res = await listsRoute.request("/", { method: "GET" });
  expect(res.status).toBe(200);
  const body = await res.json();
  expect(body).toHaveLength(1);
});

コンポーネントテスト

@solidjs/testing-library の render / screen を使用。vitest.setup.ts で @testing-library/jest-dom をインポートし、toBeInTheDocument() 等のマッチャーを有効化。

コンポーネントテストの基本パターン 
import { render, screen } from "@solidjs/testing-library";
import { Button } from "./button";

test("renders with correct variant class", () => {
  render(() => <Button variant="destructive">Delete</Button>);
  const btn = screen.getByRole("button", { name: "Delete" });
  expect(btn).toBeInTheDocument();
  expect(btn.className).toContain("destructive");
});
  • イベントは fireEvent.click(btn) または userEvent でトリガー
  • 非同期処理のあるコンポーネントは waitFor を使う
  • API 呼び出しは vi.mock("~/lib/api") で差し替える

E2E 規約

MCP Playwright ツール (mcp__playwright__*) は使用禁止。 ステップごとの往復コストが大きく、タイミング/状態ドリフトで再現性が低い。E2E は必ず pnpm test:e2e を Bash 経由で実行する。
E2E テスト規約の詳細
  • ユニーク命名 — ルーム名等は Date.now()-process.pid で並列実行時の衝突を防ぐ
  • 変更系 API の origin ヘッダ — POST/PATCH/DELETE 等は headers: { origin: "http://localhost:4321" } を付与（将来的な CSRF 対策との整合性）
  • webServer — playwright.config.ts の webServer 設定が pnpm dev を自動起動・終了するので手動管理不要
  • workers: 1 — miniflare が並列リクエストでハングする問題の回避。E2E は逐次実行
  • CI 時は retry 2 回 — ローカルは retry 1 回
  • E2E スペックは tests/e2e/ のみ。src/ には置かない
// E2E の基本パターン
test("API flow", async ({ page, request }) => {
  const roomName = `Test Room ${Date.now()}-${process.pid}`;

  // 変更系 API は origin ヘッダが必要
  const listRes = await request.post("/api/lists", {
    data: { name: roomName },
    headers: { origin: "http://localhost:4321" },
  });
  const { id } = await listRes.json();

  // SSR ページの確認
  await page.goto(`/${id}/register`);
  await expect(page.getByTestId("item-card")).toBeVisible();
});

カバレッジ設定

プロバイダ: v8。対象: src/**/*.{ts,tsx}。出力: テキスト + HTML (coverage/)。

カバレッジから除外するファイル:

  • **/*.test.* — テスト自体
  • **/*.module.css — CSS Modules
  • src/env.d.ts — 型定義のみ
  • src/server/bindings.ts — 型定義のみ
  • src/server/db/schema.ts — Drizzle スキーマ定義
  • src/pages/**/*.astro — Astro ページ（Vitest スコープ外）

カバレッジ計測: pnpm test:coverage

品質チェック順序

コミット前の標準的な確認フロー:

1
pnpm check — Biome lint/format + astro check (TypeScript)
自動修正は pnpm fix（Biome のみ。型エラーは手動修正）
2
pnpm test --run — Vitest 単体テスト（全件・非インタラクティブ）
単一ファイルは pnpm test -- src/server/routes/lists.test.ts
3
pnpm build — プロダクションビルド成功を確認
+
pnpm test:e2e — ブラウザ疎通が必要な変更時のみ（自動的に dev サーバー起動）
上記の 1〜3 は /quality-check スキルでまとめて実行できる。/quality-check --fix で Biome の自動修正も同時に行う。
